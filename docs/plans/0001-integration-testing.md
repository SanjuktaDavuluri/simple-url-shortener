# Plan 0001: Integration testing

How we prove that the parts of the shortener work **together**, across real boundaries (HTTP, Spring wiring, SQLite, Flyway, and later containers and PostgreSQL), as the system grows from v1 through the production-readiness and reliability releases. This plan is tracked: each phase has a status, an exit criterion, and the issues that deliver it.

## 1. Definitions

| Level | What it exercises | Runs with | Naming | Speed target |
|---|---|---|---|---|
| **Unit** | One unit in isolation: a Rule, the Rule Set, the Short Code generator | Maven **Surefire** (`test` phase) | `*Test` | milliseconds |
| **Integration** | The real application wired by Spring, over real infrastructure: HTTP layer, the create-Link service, Link Store, SQLite file, Flyway migrations | Maven **Failsafe** (`integration-test` / `verify` phases) | `*IT` | < 30 s for the whole suite in Release 1 |
| **System / container** (Release 2+) | The packaged artifact or Docker image, over a real network socket | Failsafe + Testcontainers | `*SystemIT` | minutes |
| **Browser** (since #8) | The running app in real Chrome: JavaScript behaviour, accessibility wiring, Lighthouse | Playwright + Lighthouse in `e2e/`, CI job **Browser checks** | `e2e/*.js` | ~1 min |
| **Performance & resilience** (Release 3) | Load and failure behaviour | Separate tooling (R13, R14), not part of `verify` | — | — |

`./mvnw verify` runs **unit and integration** tests, locally and in CI. A PR cannot merge unless both pass.

## 2. Principles

1. **Test at the agreed seams** (spec 0001): the HTTP surface and the Rule Set. Integration tests never call internal classes directly and never assert on SQL or table contents. Behaviour is observed through HTTP responses only, with one declared exception: **the Click Store, until R2** (spec 0003, seam 3; amended by #52). There is no HTTP read path for Clicks until R2's stats API, so integration tests observe stored Clicks through the Click Store's *list the Clicks for a Short Code* operation, after calling `flush()` on the Click Recorder instead of sleeping (ADR 0012). It is the interface R2 itself reads from, not a test-only back door, and tests still never read the `clicks` table or assert on SQL. Once R2 ships, the HTTP-level P8 assertions move to the stats API. A second declared exception (since #104, spec 0005 story 6): **the stored Manage Token hash**. "Only the token's SHA-256 hash is stored, never the token" is a claim about storage itself, so `IntegrationTest.storedManageTokenHash` reads `links.manage_token_hash` for one Short Code, and the V3 migration test checks that an older Link's hash is `NULL`. These are the only test reads of that column; every other Manage Token assertion goes through HTTP. Since #119 (spec 0006 seam 3), **captured log output** is a declared seam too: `OutputCaptureExtension` captures the console, tests parse every line as one JSON object and assert on fields (`log.level`, `request_id`, `route`, `status`…), never on message text, and search the raw output for values that must never appear. Since #116 (spec 0006 seam 2), the **management HTTP surface** is a declared seam too: Liveness, Readiness and the Prometheus metrics are observed over plain HTTP on the management port, which every test instance runs on a random port (`@LocalManagementPort` in `IntegrationTest`, `TestApps.managementPort`), never the maintainer's `8081`. It is the surface operators, CI and R11's container check use, not a test-only back door. The same tests also read the public port over plain HTTP, to show the servlet container answers `404` for every Actuator path.
2. **Real infrastructure, nothing mocked inside the boundary.** Integration tests use a real SQLite file migrated by Flyway, the real Spring context and real Thymeleaf rendering. The only substitutions are the **`ShortCodeGenerator`** bean, which is replaced with a scripted one so Collisions are deterministic, and (since #52) the **`Clock`**, which is replaced with a fixed one the test can move forward, so each Click's time is known in advance. Since #54, a stand-in **`ClickRecorder`** (one that blocks or throws) and a stand-in **`ClickStore`** (one that holds a batch's write transaction open, saving through the real Click Store) are swapped in, each only on its own `TestApps` instance and database file, never in the shared context, to prove the Redirect never waits for or fails because of Click recording. Since #116, two more stand-ins prove Readiness, each on its own `TestApps` instance: an **unreachable-database stand-in** (`ReadinessIT.SwitchableDataSource`, the instance's real `DataSource` until the test switches it, after which every new connection fails; removing or locking the SQLite file can't show an outage, because the pool keeps its open connections working) and a **blocked stand-in `ClickStore`** (`ReadinessIT.BlockedClickStore`, which holds every batch until released and then saves it through the real Click Store, the spec 0003 seam) with a small `CLICK_QUEUE_CAPACITY`, to fill the Click queue. Since #104, the **`ManageTokenGenerator`** is replaced with a scripted one in the shared context, so the Manage Token in a create response is known in advance; once its script runs out it draws real random tokens, so tests that don't care about the token needn't script one. Since #117 (spec 0006), a stand-in **failing handler** (a controller whose one route always throws an unexpected exception with a distinctive message) is added only on its own `TestApps` instance and database file, never in the shared context, to force a `500` over a real socket and prove it carries an `X-Request-Id` and reveals no exception message or stack trace. Since #121 (spec 0006), a stand-in **slow handler** (a controller whose one route holds its request until the test releases a latch) is added the same way, only on its own `TestApps` instance, so a request is in flight while the context closes; threads are coordinated with latches and bounded futures, never fixed sleeps.
3. **Isolation.** Integration test classes share Spring's cached application context, and with it one SQLite file, one scripted generator and one clock. **Before every test** the base class resets them: the Click Recorder is flushed first (so no Click from the previous test is written into the next test's database), Flyway rebuilds the schema from the migrations (`clean` + `migrate`, enabled only in tests), the Short Code and Manage Token scripts are emptied (since #104) and the clock is set back to its fixed time. Tests may therefore reuse Short Codes and run in any order, and every test also re-proves that the migrations apply to an empty database. (A per-class `@TempDir` doesn't work with the context cache: JUnit deletes the directory while the cached context still uses it.)
4. **Independent expectations.** Expected values come from the spec (status codes, headers, literal Short Codes from the scripted generator), never recomputed the way the code computes them.
5. **Every acceptance criterion is traceable.** Each integration test names the issue and the acceptance criterion it covers (see the traceability matrix, section 5).

## 3. Environments and fixtures

| Concern | Approach |
|---|---|
| Application context | `@SpringBootTest` + `@AutoConfigureMockMvc`, driven with `MockMvcTester` (in-process; no network). Since #116 the shared context listens on real random public and management ports (`RANDOM_PORT`, `management.server.port=0`), so `getFromPublicPort` and `getFromManagementPort` can reach them over plain HTTP |
| Real HTTP (one smoke class) | `@SpringBootTest(webEnvironment = RANDOM_PORT)` with a real HTTP client, to prove the servlet container sends 302s, `Location` and `Cache-Control` exactly as specified |
| Database | One SQLite file per Spring test context under `target/test-databases/` (removed by `./mvnw clean`); reset to an empty, freshly migrated schema before every test |
| Short Codes | `@TestConfiguration` that supplies a scripted `ShortCodeGenerator` (e.g. `AAAAAAA`, `AAAAAAA`, `BBBBBBB`) |
| Manage Tokens (since #104) | `@TestConfiguration` that supplies a `ScriptedManageTokenGenerator` (plainly fake 43-character tokens such as `first-scripted-manage-token-for-tests-00001`; real random ones once the script is empty). It counts its draws, so a test can prove a path drew no token. `createLinkForItsManageToken(longUrl)` creates a Link and returns its token; `storedManageTokenHash(shortCode)` reads the stored hash (principle 1). Expected hashes are written out in the tests, worked out with `shasum -a 256` |
| Configuration | `BASE_URL` set to a fixed test value (e.g. `http://sho.rt`) so Short URLs are predictable |
| Restart / production config | `TestApps.start(...)` starts an extra real instance (settings as command-line arguments, so they outrank `application.properties`), e.g. on the **same** database file for persistence checks |
| Requests | Shared helpers in the base class (`postLink`, `postBody`, `createLink`, `createLinkForItsManageToken`); request bodies are serialised by Jackson |
| Clicks (since #52) | A `@TestConfiguration` supplies a fixed `TestClock` (reset to `IntegrationTest.NOW`, moved forward with `advance`); `storedClicks(shortCode)` flushes the Click Recorder and lists through the Click Store; `TestApps.startWithEnvironment` starts an instance as if extra environment variables were set |
| Stand-ins and concurrency (since #54) | `TestApps.startWithConfigurations` adds `@TestConfiguration` classes (a `@Primary` stand-in) to one instance; `TestApps.port` gives its real port for an HTTP client. Threads are coordinated with latches and bounded futures (`succeedsWithin`), and `ScriptedShortCodeGenerator.awaitDraw` signals that a Link creation on another thread has drawn its Short Code, never with fixed sleeps |
| Management port (since #116) | Every test instance runs the management server on a random port: `IntegrationTest` reads it with `@LocalManagementPort`, `TestApps` passes `--management.server.port=0` and reads it with `TestApps.managementPort`. `PlainHttp` sends plain requests and parses health JSON into maps, compared whole with the expected document (so "no details" is checked too) |
| CI | GitHub Actions, Temurin JDK 25, `./mvnw verify`; Failsafe reports uploaded as build artifacts when a test fails |

## 6. Entry and exit criteria

- **Entry (per ticket):** the ticket's acceptance criteria are listed in this plan's matrix before implementation starts.
- **Exit (per ticket):** every matrix row for the ticket is ☑, `./mvnw verify` is green in CI, and the PR description links the tests.

## 7. Risks

| Risk | Mitigation |
|---|---|
| A slow Spring context makes the suite sluggish | Reuse the context across test classes (Spring's test context cache); keep scripted-generator configuration identical between classes |
| Shared context state (database, generator) leaks between tests | Reset before every test (Flyway clean + migrate, empty script); proven by a mutation check that disabling the reset breaks the suite (#14) |
| SQLite file locking between parallel tests | One database file per Spring test context; integration tests run sequentially in Release 1 |
| `MockMvcTester` hides servlet-container behaviour (headers, redirects) | The single real-HTTP smoke test (`RedirectOverHttpIT`) |
| JVM tests can't execute the page's JavaScript (HTMX swaps, copy button, focus, announcements) | `e2e/` browser checks in real Chrome, run in CI (job **Browser checks**) on every PR since #8 |
| Behaviour differs between SQLite and PostgreSQL | Contract suite in P6 before the R5 migration ships |
