# Orchestrator state stays local; the audit trail is a hash-chained event log committed to the repository; metrics are derived from it

The orchestrator (ADR 0007, ADR 0008) produces three kinds of data with different lifetimes. We keep each where its lifetime belongs:

| Data | Where | Committed? |
|---|---|---|
| **Run state** (LangGraph checkpoints, used to resume and re-plan) | SQLite at `.orchestrator/state.db` | **No** (working data, gitignored) |
| **Audit trail**: one event per stage start and end, gate result, retry, rollback, approval, re-plan, safe-stop and agent call (with its model, tokens and cost) | Append-only JSON lines per run, `delivery/runs/R-NNNN/events.jsonl` | **Yes**, through the run's own PR at close-out |
| **Run report**: graph, timeline, gates, approvals, cost | Generated Markdown, `delivery/runs/R-NNNN/report.md` | **Yes**, same PR |
| **Delivery metrics**: success rate, retry and rollback frequency, MTTR (time from a failed gate to its recovery), end-to-end latency, cost per run | `delivery/metrics.md`, regenerated by `orchestrate metrics` from every committed event log | **Yes** |

**Tamper evidence.** Every event carries the SHA-256 hash of the previous event, so editing or removing an event breaks the chain, and `orchestrate verify` checks it. Git history adds a second, independent record. Events record *who* acted (engineer, agent, CI) and *why* (the gate output, or the approval comment).

GitHub Issue comments remain the **human-readable mirror** of the run, but the event log is the system of record.

## Options considered and the trade-offs

| | Option | What we'd gain | What it would cost | Verdict |
|---|---|---|---|---|
| A | **Local checkpoints + hash-chained event log and run report committed to the repo; metrics derived** | A permanent, reviewable record that travels with the code; tamper-evident twice (hash chain and git); metrics reproducible from the raw events at any time; no infrastructure | Event logs add files to the repo; checkpoints are lost with the machine (acceptable: the event log, not the checkpoint, is the record) | **Chosen** |
| B | GitHub Issue comments as the audit trail | Visible without tooling | Unstructured; hard to compute metrics from; comments can be edited or deleted | Rejected as the system of record; kept as the mirror |
| C | Observability stack (OpenTelemetry → Jaeger/Prometheus) | Industry-standard traces and dashboards | Infrastructure to run and keep alive; the record lives outside the repo and disappears with it | Rejected for now. The event model is OpenTelemetry-compatible, so export can be added later |
| D | A database service (e.g. PostgreSQL) for runs and events | Queryable | Infrastructure for a single-repo tool; the record isn't reviewable in PRs | Rejected |

**In short:** the record of *how the software was built* lives with the software, in a form that can't be quietly edited and from which every metric can be recomputed.

## Consequences

- The event schema is versioned (`schema_version` on every event). Changing it requires migrating or tolerating older logs.
- Events must never contain secrets or credentials. A policy check enforces this before an event is written (ADR 0008 guardrails).
- `.orchestrator/` is gitignored; `delivery/` is committed.
