# Spec 0001: v1 core: shorten a Long URL and Redirect from its Short URL

Glossary: `CONTEXT.md` · Decisions: ADR 0001–0006 · Flows: `docs/architecture.md` · Deferred work: `docs/roadmap.md`

## Problem Statement

Long web addresses are awkward to share. They wrap in messages, get truncated, and are hard to read aloud or type. People want a short, stable address they can hand out, which takes whoever opens it to the original page. They also want to create one in seconds, either from a web page or from a script, without signing up.

## Solution

A small web service that turns a Long URL into a Link with a random 7-character Short Code, and gives back a Short URL (`<Base URL>/<Short Code>`). Anyone who opens the Short URL is sent on to the Long URL by a Redirect that always passes through the shortener. Links are created through a JSON API or through a single, polished web page. Every Long URL is checked against a Rule Set first, so unsafe or pointless Links (such as Self-links) are refused with a clear Rejection Reason.

## User Stories

### Creating Links: API

1. As an API client, I want to POST a Long URL and receive a Short URL, so that I can shorten links from scripts and other services.
2. As an API client, I want the response to include the Short Code, the Short URL and the Long URL, so that I don't have to parse one out of another.
3. As an API client, I want a `201 Created` status when a Link is created, so that I can tell success from failure by status alone.
4. As an API client, I want a Short URL that starts with the shortener's configured Base URL, so that it works wherever the service is deployed.
5. As an API client, I want every Short Code to be exactly 7 characters from `a–z`, `A–Z` and `0–9`, so that Short URLs are short and safe to put in any message or address bar.
6. As an API client, I want a request that is not valid JSON, or is missing the Long URL, to fail with a `422` and an explanation, so that I can fix my request.
7. As an API client, I want a rejected Long URL to fail with a `422` that carries the Rejection Reason, so that I know exactly why it was refused.
8. As an API client, I want to shorten the same Long URL twice and get two different Links, so that each Link I share is independently mine (ADR 0003).
9. As an API client, I want Short Codes that can't be guessed from previous ones, so that nobody can list other people's Links by counting.
10. As an API client, I want a `503` with an explanation if the service can't find a free Short Code after several Collisions, so that I get a clear, retryable failure instead of a hang.

### Creating Links: web page

11. As a visitor, I want a single page with one field and one button, so that I can shorten a link without reading instructions.
12. As a visitor, I want the Short URL to appear on the page without a full page reload, so that the page feels fast and modern.
13. As a visitor, I want the Short URL shown prominently with a copy button, so that I can share it in one click.
14. As a visitor, I want visible confirmation ("Copied ✓") after copying, so that I know it worked.
15. As a visitor, I want a rejected Long URL to show its Rejection Reason next to the field, so that I can correct it in place.
16. As a visitor, I want my submitted Long URL to stay in the field after a rejection, so that I can edit it rather than retype it.
17. As a visitor with JavaScript disabled, I want the form to still work as a normal form submission, so that the page never breaks.
18. As a visitor on a phone, I want the page to fit and work on a small screen, so that I can shorten links on the go.
19. As a visitor who prefers dark mode, I want the page to follow my system theme, so that it is comfortable to use.
20. As a keyboard user, I want to reach and use every control with the keyboard and see where focus is, so that I don't need a mouse.
21. As a screen-reader user, I want the field labelled and the result or Rejection Reason announced, so that I know what happened without seeing it.
22. As a visitor with low vision, I want text and controls to meet WCAG AA contrast, so that I can read everything.

### Following Links

23. As a person who received a Short URL, I want opening it to take me to the Long URL, so that the short address works like the long one.
24. As a person following a Short URL, I want the Redirect to be a `302 Found`, so that the shortener stays in the path of every Click (ADR 0005).
25. As the operator, I want Redirect responses to be marked non-cacheable, so that browsers and proxies never skip the shortener on later Clicks.
26. As a person following an unknown or mistyped Short URL, I want a clear `404 Not Found`, so that I know the Link doesn't exist rather than seeing a broken page.
27. As a person following a Short URL, I want Short Codes treated as case-sensitive, so that `Ab3xK9q` and `ab3xk9q` are distinct Links and the full code space is usable.

### Rules

28. As the operator, I want Long URLs that are not `http` or `https` (e.g. `javascript:`, `ftp:`, `mailto:`) rejected, so that Links only ever lead to web pages.
29. As the operator, I want Long URLs without a host rejected, so that every Link has a real destination.
30. As the operator, I want Long URLs longer than 2048 characters rejected, so that storage and Redirect headers stay within sane limits.
31. As the operator, I want Self-links rejected, so that nobody can build Redirect loops through the shortener.
32. As the operator, I want Self-link detection to ignore letter case in the host, so that `HTTP://LOCALHOST:8000/x` can't slip past the Rule.
33. As the operator, I want leading and trailing whitespace on a submitted Long URL ignored, so that pasted URLs with stray spaces aren't rejected.
34. As a maintainer, I want each Rule to be an independent unit with its own tests, so that I can add, change or remove a Rule without touching the create-Link flow (ADR 0004).
35. As a maintainer, I want the Rule Set to apply Rules in a fixed order and report the first Rejection Reason, so that results are predictable and messages are not confusing.
36. As a maintainer, I want every Rejection Reason written for a human, so that the API and the web page can show it as-is.

### Persistence & configuration

37. As the operator, I want Links to survive a restart of the service, so that shared Short URLs keep working.
38. As the operator, I want to set the Base URL by configuration, so that Short URLs and Self-link detection match wherever the service runs.
39. As the operator, I want the database location set by configuration, so that I can choose where data lives.
40. As the operator, I want the database to refuse duplicate Short Codes on its own, so that even a bug in the application can't make one Short Code name two Links.

### Quality & evidence

41. As an external reviewer, I want the behaviour above covered by automated tests that run with one command, so that I can verify the claims myself.
42. As an external reviewer, I want a reproducible Lighthouse run scoring 90 or more in every category for the web page, so that the "state of the art" claim is measured, not asserted.
43. As a maintainer, I want the web page and the API to share one create-Link path, so that they can never disagree about what is accepted or produced.

## Implementation Decisions

- **Stack:** Java 25, Spring Boot 4.1.1 (Spring MVC), Thymeleaf, HTMX, SQLite via `JdbcClient`, Flyway, built with the Maven Wrapper (ADR 0001, ADR 0002, ADR 0006).
- **Modules:**
  - **Application wiring:** the Spring application is assembled from three inputs: the Base URL, the database location, and a `ShortCodeGenerator` bean. Production reads the Base URL and database location from configuration (environment variables `BASE_URL`, default `http://localhost:8000`, and `DATABASE_PATH`, default `links.db`) and uses the real generator. Tests replace the generator bean with a scripted one and point the database at a temporary file. This is the main test seam.
  - **Short Code generator:** a `ShortCodeGenerator` interface whose single method takes **no inputs** and returns a 7-character base62 string. The production implementation uses `SecureRandom`. It never sees the Long URL (ADR 0003).
  - **Link Store:** the only module that touches storage. Interface: *save a Link (Short Code, Long URL), failing distinctly if the Short Code is already taken*, and *get the Long URL for a Short Code, or nothing*. v1 implementation: `JdbcClient` over SQLite, with a uniqueness constraint on the Short Code and a created-at timestamp. The schema is created by a Flyway migration (ADR 0002).
  - **Link creation (shared service):** check the Long URL against the Rule Set, then draw a Short Code and save. On a Collision, draw again, up to **5 attempts** in total. When the attempts run out, it raises a distinct "no free Short Code" failure. Both the API and the web page call this; neither has its own copy.
  - **URL Rules (`rules` package):** each Rule takes a Long URL and returns pass or a Rejection Reason. The Rule Set is an ordered list. v1 order: (1) well-formed, i.e. a syntactically valid URI (added in #16), (2) scheme is `http`/`https`, (3) host present, (4) length ≤ 2048, (5) not a Self-link, which compares scheme-less host and port against the Base URL, case-insensitively. The first failing Rule's Rejection Reason is returned. Whitespace is trimmed before the Rules run (ADR 0004).
  - **Web page:** server-rendered Thymeleaf templates. The result area is one Thymeleaf fragment used both by the full page (no-JS form post) and by the HTMX fragment response, so they can't drift. Hand-written CSS with design tokens, light and dark themes, and no build step (ADR 0006).
- **API contract:**
  - `POST /links` with JSON `{"url": "<Long URL>"}`:
    - `201` → `{"short_code": "Ab3xK9q", "short_url": "<Base URL>/Ab3xK9q", "long_url": "<as stored>"}`
    - `422` → body with a human-readable Rejection Reason (Rule failure) or a validation message (malformed request)
    - `503` → no free Short Code after 5 attempts
  - `GET /{short_code}`:
    - `302 Found` with `Location: <Long URL>` and `Cache-Control: no-store`
    - `404 Not Found` for unknown Short Codes, including strings that can't be Short Codes
  - `GET /` serves the web page. The web page's form posts to a page route that returns either the HTMX fragment or the full page, depending on whether the request came from HTMX.
- **Routing:** fixed routes (`/`, `/links`, static assets) are matched before the `/{short_code}` catch-all. Fixed routes are never 7 characters long, so they can't collide with a Short Code.
- **Stored form of the Long URL:** stored as submitted, after trimming whitespace. No other normalisation, so the Redirect goes exactly where the person intended.

## Testing Decisions

- **What makes a good test here:** it exercises **external behaviour through a seam**: HTTP requests in, status/headers/body out; or a Long URL in, pass or Rejection Reason out. Tests never reach into internals, assert on SQL, or mock our own modules. Names use glossary terms (e.g. "a Self-link is rejected with its Rejection Reason").
- **Seam 1: HTTP surface (primary).** Start the full Spring application (`@SpringBootTest`) against a temporary SQLite file (JUnit `@TempDir`, wired in through `@DynamicPropertySource`, migrated by Flyway) and drive it with `MockMvcTester`. It covers: creating Links (201 shape, Short URL uses Base URL, duplicate Long URL gives a new Link), rejections (422 with reason), malformed requests, Redirect (302, `Location`, `no-store`), unknown Short Code (404), case-sensitivity, persistence across application restarts on the same database file, the web page (full page renders; HTMX request returns just the fragment; no-JS post returns the full page with the result; rejection shown inline with the input preserved).
  - **Collisions** are tested with a **scripted `ShortCodeGenerator`** supplied as a `@TestConfiguration` bean (e.g. yields `AAAAAAA`, `AAAAAAA`, `BBBBBBB`): one Collision then success, and every attempt colliding giving a 503.
- **Seam 2: Rule Set.** Each Rule and the ordered Rule Set are tested directly with plain JUnit 5 (no Spring context): Long URL in, pass or Rejection Reason out. This covers each Rule's boundaries (exactly 2048 vs 2049 characters, scheme case, Self-link case and port variants, whitespace trimming) and first-failure ordering.
- **Real generator:** one test asserts the shape of its output (7 characters, base62 alphabet) over many draws. Randomness quality is not tested.
- **Not separately tested in v1:** the Link Store interface is covered through Seam 1. A shared contract suite for every Link Store implementation arrives with the PostgreSQL migration (roadmap R5).
- **Lighthouse:** run against the locally served page as a scripted check outside the JUnit suite; the scores are recorded with the ticket that delivers the page.
- **Prior art:** none yet (greenfield). The first tickets establish the patterns for the Spring test setup, `MockMvcTester` and the scripted generator, and later tests follow them.
- **Tooling:** JUnit 5 and AssertJ; Spotless (google-java-format) and Error Prone in the build. `./mvnw verify` runs formatting checks, compilation, analysis and every test, locally and in CI (GitHub Actions, Temurin JDK 25).
- **Integration testing** is planned and tracked in [`docs/plans/0001-integration-testing.md`](../plans/0001-integration-testing.md).
- **Process:** every ticket is built test-first (red → green → refactor) with the `tdd` skill.

## Out of Scope

- Custom aliases (R1), click counts (R2), expiring Links (R3), editing or deleting Links (R4).
- PostgreSQL (R5); the private/internal-address Rule and DNS checks (R6); scaling code generation across nodes (R7); config-driven Rules (R9).
- Clickstream / audit events (R10). v1 only guarantees every Click passes through one Redirect point.
- Docker, health endpoints, structured logging, runbook (R11, R12); load, failure and scaling tests (R13–R15).
- User accounts and Link ownership (R8: won't do).
- Authentication, rate limiting and abuse prevention. These are not on the roadmap yet. Raise them if needed before any public exposure.
- CI: GitHub Actions arrives with the GitHub repo at the end of Release 1; tests run locally until then.
